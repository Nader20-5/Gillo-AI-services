Taskove AI Service: Architecture, ML Pipeline & Build Plan

Unified specification for the AI Service, its MongoDB-AI database, custom-trained ML/LLM models, and standalone execution roadmap for Nader & Sama.

1. Service Scope & Human-in-the-Loop Model

The AI Service powers five core project intelligence features (Features 1, 2, 3, 5, and 6) alongside a centralized AI Suggestions Inbox. Proposed-task triage is removed from scope, and assignee recommendations are consolidated into Feature 1 as a reassign action.

#FeatureAI Engine UsedOutput ProducedHuman Authority
1 Sprint estimate & fit check Model 1 (Effort Regressor) + Capacity Rules Per-task hour range, sprint fit verdict (fits, tight, over), and suggested fixes (move, split, reassign) Fixes go to the Inbox: PM/TL accepts or rejects with a mandatory reason
2 Early risk warning Model 2 (Risk Classifier + SHAP Explainer) Daily detection of tasks likely to slip with step-by-step evidence Inbox: PM/TL acts on or dismisses the warning with a mandatory reason
3 Release request pre-fill Model 3 (Fine-Tuned Agile LLM) Release summary, release notes, rollback plan, and block explanation Requester reviews and edits the draft before submitting
5 Standup & retro drafts Model 3 (Fine-Tuned Agile LLM) Personal daily standup draft and sprint retrospective summary draft Owner reviews, edits, and submits the draft
6 Ask the project (Chat) Model 3 (Fine-Tuned LLM + Live Read Tools) Context-aware, source-cited answers about user tasks and project state Read-only assistant; chat has zero authority to mutate data
- AI Suggestions Inbox Shared workflow layer for Features 1 & 2 Actionable proposals with before/after previews and audit trail Managed exclusively by PM or TL (Admin is blocked everywhere)
Architectural Principle. Only actionable sprint fixes and risk warnings belong in ai_suggestions. Task estimates, sprint fit checks, text drafts, and chat sessions are non-suggestion artifacts and live in dedicated collections so the accept/reject state machine stays clean.

Dataset Strategy & Validation Framing

  • Phase 1 & 2 (Current Prototype): Pipeline validation using a parametric synthetic generator in scripts/prepare_ml_datasets.py to verify end-to-end event schemas, MongoDB persistence, and FastAPI endpoints.
  • Phase 3 (Empirical Benchmark): Empirical evaluation using the open-source TAWOS Jira benchmark dataset (Tawosi et al.).
    • Model 1: Predict real-world Cycle Time (or Story Points) against a naive median baseline.
    • Model 2: Predict mid-sprint carry-over (is_carried_over) evaluated strictly on pre-midpoint changelog snapshots to eliminate target leakage.
  • Feature Ablations: Text ablation comparing Tabular baseline vs. TF-IDF (32) vs. all-MiniLM-L6-v2 + PCA.

Read Model Collections (Synced via Kafka or Seed Script)

  • Snapshot Collections: task_snapshots, time_entries, sprint_snapshots, capacity, standup_blockers, pull_requests, and release_requests.
  • Idempotency Collection: processed_events with a unique index on event_id so redelivered Kafka messages are safely ignored.
  • Structural Privacy Guardrail: The Kafka consumer for standups explicitly strips any user mood fields before writing to standup_blockers, ensuring mood data never enters the database or reaches any model.
  • Profile Simplification: ai_profiles stores each developer's historical estimate-to-actual ratio (ratio, sample_size) required by Model 1.

Required Indexes

  • ai_suggestions: {project_id, status, created_at}, {task_id, type, status}, and a unique partial index on dedupe_key where status == "pending".
  • task_estimates: {task_id, created_at} and {sprint_id, status}.
  • chat_sessions: TTL index on last_active_at.

4. System Integration, Event Flow & Standalone Mode

In production, the AI Service consumes domain events from Kafka to keep its Read Models updated, publishes suggestion lifecycle events back to Kafka, and queries Core Agile live for Feature 6 (Chat). During development, it runs in Standalone Mode so Nader and Sama can build and test everything independently before final backend integration.

How Standalone Development Mode Works

  • 4-Sprint Seed Script: Populates all Read Model collections in MongoDB-AI with realistic history across 4 sprints (tasks, logged hours, slipped tasks, blockers without mood, PRs, release requests, and user capacities). Features 1, 2, 3, and 5 run at 100% capability on this seeded data.
  • Dual-Mode Core Agile Client (For Feature 6 Chat): Controlled via CORE_AGILE_MODE=mock|live. In mock mode, chat tools read directly from the local MongoDB Read Models filtered by the caller's JWT claims (user_id, project_id, role). When integrating with the backend team, switching to live routes requests to the Core Agile HTTP endpoints with the user's JWT.
  • Simulated Event Producer: When a PM/TL accepts a suggestion in standalone mode, the service sets apply_status = "requested", logs the outgoing AiSuggestionAccepted event payload, and optionally applies the previewed change to the local snapshot for live demo verification.

5. Feature Pipelines & API Surface

End-to-End Pipeline Logic

  • Feature 1 (Sprint Estimate & Fit Check): Calculates statistical baseline (median hours of similar tasks × assignee ratio from ai_profiles) → runs Model 1 to predict low_hours, high_hours, and confidence → saves to task_estimates. For fit check, aggregates predicted hours per user against capacity → saves verdict (fits, tight, over) in sprint_fit_checks → if tight or over, generates move, split, or reassign proposals in ai_suggestions.
  • Feature 2 (Early Risk Warning): Daily scheduled job extracts task features from Read Models (stalled days, dependency depth, repeated blockers, assignee overload) → runs Model 2 + SHAP → translates top SHAP values into structured reasoning_steps and evidence → inserts into ai_suggestions using dedupe_key to prevent duplicate pending alerts.
  • Feature 3 (Release Request Pre-Fill & Block Explainer): Reads linked tasks and pull_requests for a release → runs Model 3 to generate release_summary, release_notes, and rollback_plan drafts in ai_drafts. If blocked, analyzes incomplete tasks/unmerged PRs to produce a block_explanation draft.
  • Feature 5 (Standup & Retro Drafts): For standup, gathers the user's recent task updates, logged hours, and blockers → runs Model 3 to create a personal standup draft. For retro, aggregates sprint slippage, late-added tasks, and estimated vs. actual hours → generates a sprint retro draft in ai_drafts.
  • Feature 6 (Ask the Project Chat): Receives user question → invokes read-only tools (get_my_tasks, get_sprint_status, get_task_blockers, get_release_status) scoped to the user's JWT permissions → runs Model 3 to synthesize an answer with explicit sources → saves turn in chat_sessions.
